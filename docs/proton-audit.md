# Proton VPN / Proton Pass Morphe Patch Audit

Research only. Nothing in `morphe-pipeline` or either patch repo was modified. Repos were
cloned read-only to `/tmp/morphe-audit/{hoo-dles,rushiranpise}` at HEAD as of 2026-09-16
(`hoo-dles` @ `524` commits / latest release `v1.44.0`, `rushiranpise` @ `693` commits /
latest release `v1.22.0`) and inspected directly — Kotlin patch source, extension Java
source, `.github/workflows/*`, and full git history via `git log -p` / `git blame` / `-S`
pickaxe search. Current real-world Proton version numbers came from web search (AppBrain,
Proton's own release notes, APKMirror) — flagged as such below, not from the repos.

## Executive summary

**Proton VPN (hoo-dles, 4 patches): RELIABLE.** All four patches are small, local,
client-side-only bytecode edits to features Proton's servers have no way to gate (DNS
config, LAN routing exceptions, split-tunnel app list, a client-side delay timer). No
network code, no faked entitlements, no dependency on spoofing infrastructure. The only
real problem is staleness: the compatibility pin (`5.19.43.0`) is ~2 months old and Proton
VPN has since shipped a full minor version bump to `5.20.x` — the patches will silently
stop applying (fingerprint match failure → patch skipped or build fails) until the
maintainer bumps the pin, which is on a slow, manual, non-automated cadence for this repo.

**Proton VPN (rushiranpise, 1 patch, "Unlock VPN Plus"): CAUTION.** This is a materially
different, higher-risk patch than hoo-dles' four: it forges the account's subscription
tier object at construction time and forces every paid-feature-flag check to `true`. The
maintainer clearly understood the server-side risk — Proton's Go core validates server
access server-side — and mitigated it by silently restricting all real connections to free
servers regardless of what the UI shows. That mitigation is honest engineering, but it
also means the UI actively lies to the user (shows "Plus" tier, SecureCore/P2P/Tor hidden
but NetShield shown as available) while the account is functionally still free. NetShield
is itself a paid entitlement Proton may validate server-side on the tunnel; whether it
silently no-ops on a free connection or produces a visible failure is **unverified** from
source alone. Version pin is `5.19.78.0`; upstream is at `5.20.39.0` (per web search,
unverified against Play Store directly) — already one patch cadence behind, though this
repo bumps Proton VPN roughly every 2 weeks based on commit history, faster than hoo-dles.

**Proton Pass (rushiranpise, 1 patch, "Unlock Unlimited Plan"): CAUTION.** Local-only
bytecode patch (forges the `Plan` domain object's tier/limits at construction, in-memory,
after every server fetch) plus three shared "universal" patches it depends on
unconditionally: signature spoofing, install-source spoofing, and a Firebase cert-hash fix.
All three are verified local-only (Parcelable/Binder-level reflection tricks and DEX
call-site rewrites confined to the process) — no new network endpoints, no outbound data
added beyond what stock Firebase Installations already sends, and the source (including the
extension `.java` files, not just the patch DSL) is complete and readable, not an
obfuscated blob. The real risk is fragility, not exfiltration: the patch injects at a
**hardcoded absolute bytecode instruction index** (index `1` of `Plan.<init>`) rather than
an index computed relative to a fingerprint match. Proton Pass `1.40.3` currently still
appears to be upstream's latest Android build (per AppBrain, checked 2026-09-16,
unverified beyond that one source) — but the day it isn't, this patch has a materially
higher chance of silently mis-patching (wrong register, corrupted constructor) than
fingerprint-relative patches, rather than just failing to match and being skipped.

**Cross-cutting residual risk (applies to all three, clean patches or not):** the patched
APK is signed with morphe-pipeline's own keystore (`config/`, `README.md` — BKS keystore
generated by the `bootstrap` workflow), not Proton's. That is a deliberate, unavoidable
consequence of patching, not a bug in any of these patches: it means Play Integrity /
SafetyNet-style attestation will not see Proton's real signature (mitigated for detection
purposes by the signature-spoof patch on the Pass side, not applied on the VPN side),
Proton cannot push a signed auto-update to this APK, and — this is the one that matters
most for a VPN and a password manager specifically — **the user is trusting hoo-dles' or
rushiranpise's build pipeline and GitHub Actions credentials as much as they're trusting
Proton's.** A compromised release workflow, leaked signing key, or malicious PR merged into
either repo would be no less dangerous than it would be for the stock APK, and unlike the
stock Play Store, there's no separate app-review process gating what ships. The GitHub
Actions `attest-build-provenance` step in both repos (`release.yml`) at least gives
verifiable proof the released `.mpp` came from that specific commit/workflow run — it does
not vouch for the commit's contents being safe.

## 1. Proton VPN — hoo-dles/morphe-patches

Repo: created 2026-01-20, 1,110 stars, 37 forks, GPL-3.0, `pushed_at` 2026-09-12 (per
`gh api repos/hoo-dles/morphe-patches`). Source tree is Kotlin, fully readable, no
obfuscated assets in `patches/`. CI (`release.yml`) builds via Gradle + `semantic-release`
and attaches a GitHub build-provenance attestation to the released `.mpp`; a separate
`build_pull_request.yml` compiles every PR before merge. Compatibility target for all four
patches: `ch.protonvpn.android` version `5.19.43.0`
(`patches/src/main/kotlin/hoodles/morphe/patches/protonvpn/shared/Constants.kt:16`).

### 1a. Remove server change delay

- **File:** `patches/src/main/kotlin/hoodles/morphe/patches/protonvpn/delay/RemoveDelayPatch.kt:19-21`
- **What it does:** Finds `getChangeServerLongDelayInSeconds` and
  `getChangeServerShortDelayInSeconds` by name-fingerprint
  (`Fingerprints.kt:10-15`) and forces both to `return 0` via `returnEarly(0)`.
- **Network behavior:** None. Pure local timer value change — the delay is a client-side
  UX cooldown before allowing another server switch, not a server-enforced rate limit.
- **Detectability/account risk:** None identified. Nothing here touches account state or
  server-validated entitlements; Proton's backend has no visibility into how fast the
  client lets the user re-click "connect."
- **Fragility:** Uses named-method fingerprinting (`Fingerprints.kt`), which is resilient
  to minor internal refactors as long as the method names survive obfuscation/renaming
  (Proton doesn't appear to R8-obfuscate these method names based on the fingerprint
  design). Low fragility relative to index-based patching elsewhere in this audit.

### 1b. Unlock custom DNS

- **Files:** `patches/src/main/kotlin/hoodles/morphe/patches/protonvpn/customdns/UnlockCustomDnsPatch.kt:22-34`,
  `Fingerprints.kt:13-30`
- **What it does:** Two edits. First, in the constructor matched by
  `CustomDNSSettingViewStateCtor` (string-anchored on `"customDns"`), it replaces the
  instruction that sets the "is this restricted" register with `const/4 v$reg, 0x0`
  (line 27) — i.e., the settings screen always reports custom DNS as unrestricted.
  Second, in `applyRestrictions` on `BaseApplyEffectiveUserSettings`
  (`Fingerprints.kt:24-29`), it removes the instruction one before the `getCustomDns()`
  call (line 32) — deletes whatever gate previously ran before the app decided to apply
  the user's custom DNS setting.
- **Network behavior:** None. Custom DNS is a client-side resolver setting Proton's VPN
  server doesn't need to authorize — the client picks the DNS server it queries.
- **Detectability/account risk:** None identified — this is not a feature the VPN gateway
  can contradict or enforce; it's local resolver configuration.
- **Fragility:** Fingerprint-relative index math (`instructionMatches.last().index - 1`),
  not hardcoded. More resilient to unrelated code shifting around the matched region than
  a literal instruction-number patch, though it will still break if Proton reorders/adds
  instructions inside the matched window itself.

### 1c. Unlock LAN connections

- **Files:** `.../lan/UnlockLanConnectionsPatch.kt:23-33`, `Fingerprints.kt:14-23`
- **What it does:** Same two-part pattern as custom DNS: forces the "restricted" flag to
  `0` in the LAN settings view-state constructor (anchored on the
  `settings_advanced_allow_lan_description` string resource, `Fingerprints.kt:17`), and
  strips the pre-`getLanConnections()` gate instruction in `applyRestrictions`.
- **Network behavior:** None. LAN access during VPN tunneling is a routing-table decision
  made entirely on-device (whether local subnet traffic bypasses the tunnel).
- **Detectability/account risk:** None identified — same reasoning as custom DNS: this is
  not a server-authorized capability.
- **Fragility:** Same fingerprint-relative pattern as 1b — moderate resilience.

### 1d. Unlock split tunneling

- **Files:** `.../splittunneling/UnlockSplitTunnelingPatch.kt:23-33`, `Fingerprints.kt:13-20`
- **What it does:** Same pattern again, anchored on the `"currentModeAppNames"` string.
  Forces the restriction flag to `0` in the constructor and strips the
  `getSplitTunneling()` pre-check in `applyRestrictions`.
- **Network behavior:** None. App-list-based tunnel exclusion is resolved locally by the
  VPN client's packet routing, not the server.
- **Detectability/account risk:** None identified.
- **Fragility:** Same fingerprint-relative pattern — moderate resilience.

### hoo-dles / Proton VPN verdict: **RELIABLE**

All four patches are genuinely local-only — they touch client-side settings gates, not
server-validated entitlements, so there's no "server rejects the unlock" failure mode to
worry about (question 3 doesn't really apply here — these aren't things Proton's servers
check at all). No dependency on signature/install-source/Firebase spoofing infrastructure,
no extension DEX blobs, complete readable source. The one real weakness: the version pin
(`5.19.43.0`, bumped 2026-07-16 per `git log -S -- .../shared/Constants.kt`) has not moved
in two months while Proton VPN has shipped a full `5.20.x` minor bump (per web search —
**unverified against Play Store directly**, sourced from Proton's own release-notes page
and APKMirror). Under `compatibleWith(single exact version)`, that means these patches will
likely simply refuse to apply (fail-closed) against current Proton VPN builds rather than
silently mis-patch — annoying, not dangerous, but worth knowing before assuming the daily
pipeline build is actually current.

## 2. Proton VPN — rushiranpise/morphe-patches ("Unlock VPN Plus")

Repo: created 2026-06-01 (younger than hoo-dles), 680 stars, 44 forks, GPL-3.0,
`pushed_at` 2026-09-15 (per `gh api`). This is a large multi-app bundle repo (`Constants.kt`
alone lists hundreds of unrelated apps — Proton VPN is one of ~200+ entries), which changes
the trust calculus slightly: a much bigger attack surface and contributor base than a
Proton-focused repo, though commit history shows no sign of anything unusual around the
Proton entries specifically.

- **Files:** `patches/src/main/kotlin/app/template/patches/protonvpn/premium/ProtonVpnPremiumPatch.kt`
  (execute block: lines 41-160), `Fingerprints.kt` (all fingerprints), compatibility target
  `ch.protonvpn.android` `5.19.78.0` (`shared/Constants.kt:1280`).
- **What it does (verified against source, not just the in-file comments):**
  - Injects `subscribed=1` and `maxTier=Integer(3)` directly into `VpnUser.<init>` at
    hardcoded instruction indices 11 and 22 (`ProtonVpnPremiumPatch.kt:47-63`) — i.e., it
    fabricates a top-tier ("PMTeam/Visionary") account object at construction time, then
    additionally patches six getters (`getUserTier`, `getMaxTier`, `isFreeUser`,
    `isUserPlusOrAbove`, `getUserTierName`) to hardcode the same lie for any already-cached
    `VpnUser` instances (lines 66-77).
  - Forces `hasAccessToServer`, `haveAccessWith`, and `ServerGroup.getAvailable` to always
    return true/allow (lines 80-82) — these are the client-side gates for "can I connect to
    this server."
  - **Then, separately, hard-restricts the actual server pool to free servers only**: the
    countries-tab list filter is rewritten to hide any non-free server
    (`ProtonVpnPremiumPatch.kt:87-102`), and `getBestScoreServer` — the function that picks
    which server a connection attempt actually lands on — is patched to pre-filter its
    input to `isFreeServer() == true` before scoring (lines 105-129). The patch's own
    top-of-file comment (`ProtonVpnPremiumPatch.kt:28-32`) states the reason explicitly:
    *"ProtonVPN's Go core validates session server-side — Plus servers reject free
    accounts."* This is the maintainer correctly identifying and working around the
    server-side entitlement check rather than shipping something that would break VPN
    connections outright.
  - Forces every feature flag check (`IsFeatureFlagEnabledImpl.invoke`) to return `true`
    unconditionally (line 132) — not scoped to VPN-specific flags, *all* remote/local
    feature flags in the app.
  - Forces `NetShieldAvailability` to `AVAILABLE` (lines 134-137) and hides
    SecureCore/P2P/Tor filter tabs since those aren't reachable on free servers
    (lines 140-144).
- **Network behavior:** No new endpoints or outbound calls added — this is entirely local
  object/bytecode manipulation of values already in memory. It doesn't need to talk to any
  server to fake the tier; it just prevents the (also client-side) UI/routing logic from
  acting on the real tier value.
- **Detectability/account risk — this is the one to flag:** The patch's own design
  acknowledges the core risk (server-side entitlement checks) and neutralizes it for actual
  server connections by force-restricting to free servers. But two things are **not**
  neutralized:
  1. The UI actively misrepresents the account as Plus/PMTeam tier while it functionally
     still behaves as free — a "clean" unlock in the sense of not breaking, but a
     misleading one in the sense of showing capability the account doesn't have and never
     will use.
  2. `NetShieldAvailability` is forced to `AVAILABLE` (line 135), but NetShield is itself a
     paid-tier feature. Whether Proton's tunnel gateway silently ignores a NetShield
     request from a free-tier connection, or whether enabling it against a free-server
     connection produces a visible error/failure, is **unverified** — the source shows the
     client-side flag being forced, not what Proton's server does when NetShield is
     requested on a free-server session. This is exactly the "client-side unlock the
     server can contradict" failure mode the audit asked about; I can't confirm from
     static source alone whether it silently no-ops or actively breaks.
  3. Forcing *all* feature flags to enabled (line 132) is broader than the paywall — it
     will also flip on any experimental/staged/internal flag Proton ships behind the same
     mechanism, which could enable half-finished UI paths not intended for production use.
     This is a reliability risk (the "breaks silently" failure mode from the task's opening
     framing) more than a security one.
- **Fragility:** Meaningfully worse than the hoo-dles patches. The tier-injection edit
  (`addInstructions(11, ...)` and `addInstructions(22, ...)`, lines 47-63) uses **hardcoded
  absolute instruction indices** into `VpnUser.<init>`, not indices computed relative to a
  fingerprint match. The fingerprint (`VpnUserConstructorFingerprint`,
  `Fingerprints.kt:202-221`) correctly locates the right constructor by class/name/exact
  parameter list, but once located, the patch assumes the *internal* instruction layout at
  indices 10-22 is exactly what the maintainer observed when reverse-engineering
  `5.19.78.0`'s smali (per the extensive inline comments documenting the exact register
  layout, e.g. lines 20-32 of `Fingerprints.kt`). If a future Proton VPN build adds one
  instruction before index 10 (e.g., an extra null-check, a new field, a Kotlin compiler
  version bump changing codegen), this silently inserts the injected bytecode in the wrong
  place instead of failing to match — a worse failure mode than hoo-dles' fingerprint-only
  patches, which fail closed. Version history
  (`git log -S -- shared/Constants.kt`) shows this repo bumps the Proton VPN pin roughly
  every 2 weeks (`5.19.43.0`→`5.19.61.0` 2026-07-23, →`5.19.78.0` 2026-08-07) but nothing
  since — 40 days stale as of 2026-09-16, and upstream has moved a full minor version to
  `5.20.39.0` (web search, unverified against Play Store).

### rushiranpise / Proton VPN verdict: **CAUTION**

Not "not recommended" — the maintainer clearly did the hard part correctly (server-side
entitlement checks are real and handled), and there's no data exfiltration risk. But this
is a meaningfully riskier patch than hoo-dles' four: it fabricates account state rather
than toggling client-only settings, it leaves at least one unverified server-contradiction
point (NetShield), it over-broadly force-enables all feature flags rather than just paywall
ones, and its core injection is hardcoded-index rather than fingerprint-relative, so a
version bump is more likely to silently mis-patch than cleanly fail. If you want a
Proton VPN unlock, hoo-dles' four narrower patches are the lower-risk choice for the
features they cover (DNS/LAN/split-tunnel/delay); this patch is the only way to get actual
paid-server access unlocked client-side, but note the free-server-only restriction means
you don't actually get Plus servers — you get a Plus-looking UI on a free connection.

## 3. Proton Pass — rushiranpise/morphe-patches ("Unlock Unlimited Plan")

Same repo as above (created 2026-06-01, 680 stars). Compatibility target: `proton.android.pass`
version `1.40.3` **exactly** (`shared/Constants.kt:1272`, `versionCode = 14003373`), strict
single-version pin, `default = true` (auto-applied when this app is patched —
`ProtonPassUnlockPatch.kt:88`).

- **File:** `patches/src/main/kotlin/app/template/patches/protonpass/ProtonPassUnlockPatch.kt`
  (execute block: lines 98-115), fingerprint:
  `patches/src/main/kotlin/app/template/patches/protonpass/Fingerprints.kt:67-79`.
- **What it does:** Injects 10 instructions at index `1` of `Plan.<init>` — i.e.,
  immediately after `super.<init>()` and before the constructor's first field write
  (`ProtonPassUnlockPatch.kt:99-114`). It constructs a `PlanType$Paid$Plus("pass2023",
  "Proton Pass Plus")` object and substitutes it for the real `planType` parameter, then
  overwrites `vaultLimit`/`aliasLimit`/`totpLimit` params with `PlanLimit$Unlimited.INSTANCE`
  and forces `hideUpgrade = true`. The extensive header comment
  (`ProtonPassUnlockPatch.kt:10-82`) documents *why* — a documented prior failed attempt
  that only patched `hideUpgrade`/limits and missed that several view models
  (`ProfileViewModel`, `SecurityCenterHomeState`, `SelectItemViewModel`, `AuthViewModel`,
  `CanPerformPaidActionImpl`) do `instanceof PlanType$Paid` checks directly, bypassing the
  limit-only patch. This constructor-injection approach means every derived boolean
  (`isPaidPlan`, `isFreePlan`, `isBusinessPlan`) is computed *by the real, unmodified
  constructor code* from the forged `planType`, rather than needing separate patches per
  getter — a materially cleaner technique than the "patch every getter" approach used in
  the Proton VPN patch above.
- **Dependencies (auto-applied, not optional when this patch is selected) —
  `ProtonPassUnlockPatch.kt:92-96`:**
  1. **`spoofSignatureVerificationPatch`**
     (`shared/signature/SpoofSignatureVerificationPatch.kt`) — installs
     `SignatureHookApp` as the `Application` superclass
     (`extensions/extension/src/main/java/.../SignatureHookApp.java`), which intercepts
     `PackageInfo.CREATOR`'s Parcel deserialization and swaps the re-signed APK's
     certificate back to Proton's original one, purely via reflection on in-process fields
     (`PackageInfo.CREATOR`, `PackageManager.sPackageInfoCache`, `Parcel.mCreators`) —
     verified in `SignatureHookApp.java:28-141`, no network code anywhere in the class.
     Explicitly documented as *not* bypassing Play Integrity/hardware attestation
     (`SpoofSignatureVerificationPatch.kt:117`).
  2. **`spoofInstallSourcePatch`** (`shared/installer/SpoofInstallSourcePatch.kt`) —
     rewrites DEX call sites that read the installer package name, plus a Binder-level
     `Proxy` over `ActivityThread.sPackageManager`
     (`extensions/.../InstallSourceHelper.java:41-157`) so the app always reports
     `com.android.vending` (configurable) as its installer. Verified local-only:
     reflection over `ActivityThread`/`ApplicationPackageManager`/`ServiceManager` fields,
     no outbound calls.
  3. **`spoofFirebaseCertHashPatch`** (`shared/firebase/SpoofFirebaseCertHashPatch.kt`) —
     overrides `FirebaseInstallationServiceClient.getFingerprintHashForPackage()` and the
     `X-Android-Cert` HTTP header value to return Proton's *original* cert SHA-1 instead of
     the re-signing pipeline's cert. **Note for the network-behavior question:** this does
     modify the content of an outbound HTTP header sent to Google's Firebase Installations
     service — but it doesn't add a new destination or new data; it changes an existing
     header's value to match what Proton's real build would have sent, specifically so
     push notifications / Remote Config keep working post re-signing. It is, in effect,
     telling Google's servers the app's signature is something it isn't — a real if
     narrowly-scoped deception aimed at a third party (Google), not the user.
- **Network behavior overall:** No new endpoints, no telemetry, no exfiltration path
  identified anywhere in the patch or its three dependencies. All three "universal" spoof
  patches operate via local reflection/Parcelable/DEX tricks confined to the process; the
  one HTTP-adjacent change (Firebase cert header) modifies an existing header's value
  rather than adding a new outbound call. Source for every file touched, including the two
  Java extension classes, is present and readable — no compiled/obfuscated blobs shipped
  separately.
- **Detectability/account risk:** Proton Pass's paid features (vault/alias/TOTP limits,
  dark web monitoring, item sharing, secure links) are gated by data Proton's server
  returns and caches locally (`PlanRepositoryImpl → PlanEntity (Room) → Plan`, per
  `Fingerprints.kt:9`) — but consumption/creation of items is otherwise a **local
  database operation**, not something the server validates per-write the way VPN server
  access is. That's the key structural difference from the VPN patch: there's no equivalent
  "server rejects the unlock on use" moment for most of what this patch touches, because
  Pass's vault operations aren't gated live per-request the way VPN server admission is.
  The exception worth flagging: **sharing features (item sharing, secure links)
  do involve server-side coordination with other accounts/recipients** — those could
  plausibly be checked server-side at the point of the *recipient's* client or server
  processing, not just locally. This is **unverified**: nothing in the patched files
  confirms or rules out server-side re-validation of sharing-related paid actions.
- **Fragility:** Same hardcoded-index weakness as the VPN patch —
  `addInstructions(1, ...)` in `Plan.<init>` (`ProtonPassUnlockPatch.kt:99-114`) assumes
  the constructor's instruction layout is exactly what's documented in the fingerprint file
  header (`Fingerprints.kt:39-60`, an explicit smali listing for `1.40.3` specifically).
  Register reuse (`p3`/`p4`/`p5` as scratch before restoring them, documented in
  `ProtonPassUnlockPatch.kt:49-63`) makes this *more* index-sensitive than the VPN patch,
  not less — an off-by-one from a future compiler/field change doesn't just miss the
  injection point, it could corrupt a constructor parameter register used later in the
  same method. Given the version pin is exact (`1.40.3` only, no range), a mismatched build
  should fail to compile/apply outright (`compatibleWith` checks the target version before
  the patch runs) rather than silently mis-patch a *different* version — so the real-world
  risk window is narrower than it sounds, contingent on the pipeline never skipping the
  compatibility check.
- **Pin cadence:** Added 2026-08-15/16 (`git log -S"proton.android.pass"`), never bumped
  since — 32 days stale as of 2026-09-16. Per AppBrain (web search, **unverified against
  Play Store directly**), `1.40.3` was still Proton Pass's latest Android build as of the
  time of that search, last updated 2026-07-28 — so unlike Proton VPN, this pin may
  currently still be current. That's fortunate timing, not evidence the maintainer updates
  Pass pins faster than VPN pins; there's only one pin event to judge cadence from.

### rushiranpise / Proton Pass verdict: **CAUTION**

Local-only, no exfiltration, complete and readable source including the extension DEX
source — better than a lot of ReVanced-ecosystem patches on that front. The three
dependency patches are individually clean and well-documented, even the one modifying an
outbound Firebase header. The reasons this isn't a flat RELIABLE: (1) the exact-version
pin plus hardcoded-index injection into a password manager's core plan object is a higher
consequence combination than the same technique on a VPN UI toggle — if this ever does
silently mis-patch instead of failing closed, it's mis-patching the object that gates
whether your vault data has limits, not a cosmetic setting; (2) sharing-feature server-side
re-validation is unverified and is the one place this patch's "local-only" story could
break down; (3) `default = true` means anyone patching Proton Pass gets this — and the
three spoof dependencies — without a separate opt-in decision, which is convenient but
means less deliberate exposure to the signature/install-source/Firebase spoofing surface
than an opt-in default would give.

## Notes on what wasn't verified

- **Release `.mpp` vs. source match:** Not verified by decompiling the published `.mpp`
  artifacts and diffing against source — verified indirectly via (a) both repos' CI
  workflows building directly from the checked-out `dev`/`main` tree with no separate
  injection step, and (b) both attaching `actions/attest-build-provenance` to the release
  artifact, which cryptographically ties the published `.mpp` to a specific commit/workflow
  run (verifiable via `gh attestation verify`, not run here). This proves the artifact
  matches *some* CI run of *this repo* — it does not independently prove that commit's
  contents are safe, which is what the rest of this document assesses via source reading.
- **Live server-side behavior** (does NetShield silently no-op on a free-tier connection;
  does Proton Pass sharing get re-validated server-side) — both explicitly marked
  unverified above; would require an actual patched build + live account to confirm.
- **Current Play Store version numbers** for both apps came from web search (Proton's own
  release-notes blog, AppBrain, APKMirror), not from querying the Play Store directly —
  reasonable confidence, not certainty, and flagged inline wherever used.
